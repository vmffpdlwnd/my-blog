# 작업 규칙

사용자와 AI가 같이 작업할 때 지키는 규칙입니다. AI는 작업 전에 이 문서를 읽습니다. ([CLAUDE.md](../CLAUDE.md)에서 안내)

## 깃 규칙

커밋 제목은 `type: 내용` 형식입니다.

| type | 언제 |
| --- | --- |
| `fix` | 버그를 수정한 경우 |
| `feat` | 새로운 기능을 추가한 경우 |
| `docs` | 문서를 수정한 경우 |
| `test` | 테스트 코드를 추가한 경우 |
| `refactor` | 코드 리팩토링을 한 경우 |
| `style` | 코드 의미에 영향을 주지 않는 변경사항인 경우 (코드 포맷 변경, 세미콜론 추가 등) |
| `chore` | 빌드 부분 혹은 패키지 매니저를 수정한 경우 |
| `BREAKING CHANGE` | 커다란 API 변경의 경우 (API의 arguments, return 값의 변경, DB 테이블 변경, 급하게 치명적인 버그를 고쳐야 하는 경우). 본문이나 푸터의 시작 부분에 `BREAKING CHANGE: 설명`을 추가한다. 제목에 `!`를 추가해 표시할 수도 있다 |
| `comment` | 주석을 추가한 경우 |
| `rename` | 파일 혹은 폴더명을 수정하거나 옮기는 작업을 수행한 경우 |
| `remove` | 파일 혹은 폴더를 삭제한 경우 |
| `design` | css 등 사용자 UI 디자인 변경 |
| `ongoing` | 개발 진행 중 중간 저장이 필요한 경우 |
| `temp` | 임시 기능을 구현해야 하는 경우 |

- 커밋은 Fork로 한다. 첫 줄이 제목, 둘째 줄부터 본문이면 Fork가 알아서 구별한다.
- 브랜치 이름은 `feat/`, `docs/`, `rename/`처럼 type을 앞에 둔다.
- 머지가 끝난 브랜치도 지우지 않고 남긴다.

## 작업 규칙

### 시작 트리거 (절대 규칙)

- 사용자가 **"다음 작업 하자"**라고 말하기 전에는 작업을 시작하지 않는다. 파일도 만들지 않는다.
- 그 말이 없으면 단순히 의견을 나누고 싶다는 뜻이다.
- "다음 작업 하자"는 **최신 커밋을 기준으로, todo에서 지금 해야 할 작업을** 하자는 뜻이다. 최신 커밋을 먼저 확인하고, 아직 안 끝난 작업이 있으면 그 작업을 한다.
- "todo"는 할 일을 정리해 보자는 뜻이다. **추천 브랜치명을 포함한 표**로 할 일만 정리하고, 작업(파일 표, 수정 코드 등)은 만들지 않는다.

### 작업 정리 형식

"다음 작업 하자"라고 하면 **한 번의 답변 안에** 아래 5가지를 모두 넣는다.

1. **수정/추가될 파일 목록**: 표로 만든다. 왼쪽은 구분(`root`, `pages`, `assets`, `content`, `data`, `scripts`, `docs`)만, 오른쪽은 파일명. 파일이 실제로 있는 폴더로 구분한다. 추가하는 파일은 사용자가 작업 전에 먼저 만들 수 있게 표시한다.
2. **수정되는 스크립트**: 수정하는 만큼 사용자가 알아볼 수 있어야 한다. 핵심은 **"~ 함수 밑에", "~ 주석 위에"처럼 위치를 자세하게** 알려 주는 것이다. 테스트처럼 파일 양이 많으면 파일 통째로 올린다.
3. **커밋 내용**: 첫 줄 제목, 둘째 줄부터 본문.
4. **다음 작업 요약**: 다음 작업을 간단히 정리한다. 사용자가 이걸 보고 PR을 쓸지 계속 작업할지 정한다.
5. **완성된 파일**: 수정하거나 추가한 파일의 완성본을 **그 답변에서 바로** 올린다. "위에서 올린 파일"처럼 이전 답변의 파일을 가리키지 않는다. README와 기획서 같은 문서는 **풀버전**으로 올린다.

### 설명 방식

- 핵심만 짧게 말한다. 묻는 것에만 답한다.
- 이동한 파일과 내용을 수정한 파일을 섞어서 설명하지 않는다.

### 그 밖의 약속

- 작업이 끝나면 [`작업현황.md`](작업현황.md)를 갱신해서 5번 완성 파일에 포함한다.
- 파일을 추가, 이동, 삭제했으면 [`CLAUDE.md`](../CLAUDE.md)의 코드 지도도 같이 갱신한다.
- 링크나 경로를 바꾸면 테스트 글을 만들어 깨진 링크가 없는지 확인한다.
